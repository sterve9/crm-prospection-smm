12. Stratégie de Tests
Périmètre de ce fichier
Ce fichier décrit la stratégie de validation appliquée au système : les types de tests effectués, les cas couverts, les cas limites identifiés, et les limites assumées de la couverture.

Ce fichier ne détaille pas l'implémentation (voir 11.Plan_Implementation.md) ni la documentation utilisateur (voir 13.Documentation.md).

1. Philosophie de validation
Le système est un outil interne à faible criticité : pas de flux financier, pas de communication sortante automatisée, pas de données sensibles au sens RGPD strict.

En conséquence, la stratégie de tests est pragmatique et manuelle, pas exhaustive ni automatisée.

Principes retenus :

Chaque brique externe validée isolément avant intégration
Chaque workflow validé de bout en bout avec des données réelles
Les cas limites identifiés en exécution réelle sont documentés et corrigés
Pas de suite de tests automatisés (choix assumé, voir section 6)
2. Types de tests appliqués
2.1 Tests unitaires manuels (par nœud)
Chaque nœud a été testé individuellement dans l'interface du moteur d'orchestration, avec des données d'entrée contrôlées, avant d'être connecté au nœud suivant.

Méthode :

Utilisation du mode "Execute Node" pour tester un nœud isolé
Vérification visuelle de la sortie JSON
Correction du mapping ou de la logique si nécessaire
Nœuds concernés : tous les nœuds des 2 workflows.

2.2 Tests d'intégration par bloc
Chaque bloc fonctionnel (voir 06.Composants.md) a été testé de bout en bout après assemblage de ses nœuds.

Méthode :

Exécution du bloc complet avec des données d'entrée réalistes
Vérification que la sortie du bloc correspond au contrat attendu (voir 07.Contrats.md)
Blocs concernés : les 6 blocs des 2 workflows.

2.3 Tests de bout en bout par workflow
Chaque workflow a été exécuté complètement, du trigger à la sortie, avec des données réelles.

WF1 testé avec :

Requête : divers métiers (sophrologue, boulanger, coiffeur, etc.)
Zone : diverses villes françaises
Limite : 1, 10, 30, 100 prospects
WF2 testé avec :

Différents id_campagne existants en base
Prospects avec et sans site web
Prospects avec et sans réseaux sociaux
2.4 Test d'intégration inter-workflow
Vérification que WF1 déclenche correctement WF2 et transmet l'id_campagne.

Méthode :

Lancement d'une prospection complète via le formulaire
Vérification en base que la campagne est bien clôturée
Vérification dans le tableur que les prospects apparaissent enrichis
Vérification des logs d'exécution des 2 workflows

4. Cas limites identifiés
4.1 Volume élevé (100+ prospects par campagne)
Comportement observé : l'appel IA se fait séquentiellement (un prospect à la fois). Pour 100+ prospects, la durée d'exécution devient significative (plusieurs minutes).

Impact utilisatrice : aucun bloquant, mais nécessite de la patience. Le tableur se remplit progressivement.

Non résolu à ce jour. Voir 10.Justifications.md (D-12).

4.2 Coût cumulé des appels IA
Comportement observé : chaque prospect génère 1 appel au moteur IA. Le coût cumulé peut monter si l'utilisatrice lance de nombreuses campagnes volumineuses.

Mitigation actuelle : limite dure de 120 prospects par campagne (validation en amont).

4.3 Fragilité du trigger inter-workflow
Voir 10.Justifications.md (D-07). Le passage d'id_campagne entre WF1 et WF2 se fait par passthrough sans mapping explicite. Non détecté en usage nominal, mais point de vigilance.

5. Environnements de test
5.1 Environnement de développement
Contexte : instance du moteur d'orchestration en mode édition, avec accès aux mêmes services externes que la production.

Précaution : pendant le développement, le trigger inter-workflow (WF1 → WF2) a été temporairement désactivé pour éviter d'écrire des données de test dans le tableur final.

5.2 Environnement de production
Contexte : mêmes workflows, activés. Les données de test préalablement injectées ont été purgées avant mise en service.

6. Ce qui n'est PAS testé (limites assumées)
6.1 Pas de suite de tests automatisés
Le système ne dispose pas de tests automatisés (pas de framework de test, pas de CI/CD, pas d'assertions programmatiques).

Raison assumée : le système est un outil interne à utilisateur unique, avec un faible taux d'évolution. Le coût de mise en place d'une suite de tests automatisés dépasserait le bénéfice.

Point de bascule : si le système est étendu à plusieurs utilisateurs ou si le taux d'évolution augmente, une suite de tests devra être introduite.

6.2 Pas de tests de charge
Le comportement du système au-delà de 120 prospects par campagne n'a pas été testé (la limite dure empêche d'y arriver).

6.3 Pas de tests de résilience
Le comportement du système en cas de panne partielle d'un service externe (base indisponible, moteur IA en erreur, API de collecte hors service) n'a pas été systématiquement testé.

Comportement attendu par défaut : le workflow s'arrête sur l'erreur, les données déjà écrites en amont restent en place, l'exécution est visible dans les logs du moteur d'orchestration pour diagnostic manuel.

7. Validation utilisatrice
État actuel : validation fonctionnelle par l'équipe de développement effectuée.

Validation métier (par l'utilisatrice finale) : à réaliser en usage réel.

Critères de validation métier attendus :

Les prospects livrés correspondent bien à la requête
Les recommandations IA (angle, accroche, priorité) sont exploitables
Le format de restitution dans le tableur est utilisable sans formation
La qualification manuelle est simple et rapide
