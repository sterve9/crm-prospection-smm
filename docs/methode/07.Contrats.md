## Périmètre de ce fichier

Ce fichier décrit les contrats de données qui circulent entre les blocs du
système. Un contrat de données définit :

- l'**émetteur** (bloc source)
- le **récepteur** (bloc cible)
- la **structure exacte** des champs échangés (nom, type, origine)
- les **règles ou contraintes** attachées

Les contrats sont extraits fidèlement des workflows n8n réels, pas d'une
reconstruction théorique.

## Vue d'ensemble

Le système fait circuler **12 contrats** de données au total :

- **7 contrats** internes au Workflow 1
- **1 contrat** inter-workflow (WF1 vers WF2)
- **4 contrats** internes au Workflow 2

## CT-04 — Prospects bruts Apify **[révisé 04/09]**

**Source :** C03-N02 (HTTP POST vers Apify API)
**Cible :** C04-N01 (Nettoyage)

**Endpoint :** `api.apify.com/v2/acts/nwua9Gu5YrADL7ZDj/run-sync-get-dataset-items`

### Payload envoyé — révisé le 04/09/2026

| Paramètre | Valeur |
|---|---|
| `searchStringsArray` | `[ search ]` — **le métier seul** |
| `locationQuery` | `location` — **paramètre géographique dédié** |
| `maxCrawledPlacesPerSearch` | `maxResults` |
| `language` | `"fr"` |
| `countryCode` | `"fr"` |
| `skipClosedPlaces` | `true` |
| `scrapeContacts` | `true` |
| `scrapeSocialMediaProfiles` | `facebooks`, `instagrams`, `tiktoks` à `true` |

⚠️ **Ce qui a changé, et pourquoi.**
Le payload d'origine envoyait `searchStringsArray: [ search + " " + location ]`
— la zone était **concaténée à la recherche**. Google Maps trouvait alors
le nom de la ville dans les **noms de rue** : une recherche « boulangerie »
+ « lyon » renvoyait des boulangeries d'Ambert, de Savigneux et de
Dordogne, situées sur des « avenues de Lyon », à 400 km de la zone
demandée. Le résultat était de surcroît **instable** — deux exécutions
identiques ne donnaient pas la même géographie.

`locationQuery` est le paramètre dédié de l'acteur. Après correction :
cinq prospects sur cinq à Lyon 69009, puis cinq sur cinq à Lyon 69006.

⚠️ `scrapeContacts` et `scrapeSocialMediaProfiles` font visiter chaque site
web **par Apify**. Le coût par résultat et la durée du run augmentent.
Mesure du 04/09 : **34 secondes pour 5 prospects**. L'endpoint synchrone a
une limite de l'ordre de 5 minutes — **non éprouvé au-delà de 5 prospects.**

## CT-12 — Prospect enrichi et vérifié **[nouveau 04/09]**

**Source :** C04-N02 (Code JS — Contacts et cohérence)
**Cible :** C05-N01 (Insert collectes) ET C05-N02 (Upsert prospects)

Ce contrat n'existait pas. Il a été créé le 04/09/2026 pour **décider quels
contacts appartiennent réellement au prospect**.

### Le problème qu'il résout

Pour la boulangerie « Le 9ème Pain » (Lyon 9ᵉ, 252 avis), Apify a renvoyé :

```
facebooks   facebook.com/lws.fr        → "LWS | Paris", 170 458 abonnés
instagrams  instagram.com/lws_lws.fr
youtubes    youtube.com/@LwsFrance
```

Ce sont les réseaux de **LWS, l'hébergeur du site**, présents dans le pied
de page du template. Livrées telles quelles, ces données auraient fait
démarcher « une boulangerie à 170 000 abonnés ».

### Les deux preuves d'appartenance

Un profil social n'est retenu que si **l'une** est vraie :

1. **Preuve de domaine** — l'hôte de `externalProfileURL` est égal à
   `domain`. Pour Maison Deschamps : `maison-deschamps.com` des deux côtés.
2. **Preuve de nom** — le `username` ou le `profileName` contient un mot
   distinctif de l'enseigne, d'au moins 5 caractères.

⚠️ La preuve 2 existe parce que **beaucoup de comptes mettent un Linktree**
en lien externe : la preuve 1 seule rejetait de vrais comptes.

Les mots de métier trop génériques sont exclus de la comparaison —
`boulangerie`, `boulanger`, `patisserie`, `restaurant`, `maison`,
`artisan`, `viennoiserie`, `traiteur`, `france`, `lyon`, `paris` — sinon
n'importe quel compte correspondrait à n'importe quel commerce.

### Champs produits

| Champ | Type | Règle |
|---|---|---|
| `email` | string | `emails[0]`, sinon `facebookProfiles[].email` **d'un profil vérifié** |
| `facebook` | string | URL du profil vérifié, vide si rejeté |
| `instagram` | string | URL du profil vérifié, vide si rejeté |
| `linkedin` | string | **uniquement une page `/company/`** |
| `instagram_abonnes` | number | `followersCount` du profil vérifié, sinon 0 |
| `instagram_publications` | number | `postsCount` du profil vérifié, sinon 0 |
| `facebook_abonnes` | number | `likes` du profil vérifié, sinon 0 |
| `fiche_non_revendiquee` | boolean | `claimThisBusiness` |
| `enrichissement` | string | l'état de la détection, **réseau par réseau** |

**Deux règles supplémentaires, chacune née d'une mesure :**

- **LinkedIn sur `/company/` uniquement.** Le 04/09, `linkedIns[0]` valait
  `linkedin.com/in/jessica-helme` pour la « Boulangerie des Canuts » — un
  profil **personnel**, probablement la personne ayant fait leur site.
- **L'email vient du profil Facebook vérifié.** Le champ `emails[]` était
  vide sur les cinq prospects mesurés ; l'email de Maison Deschamps se
  trouvait dans `facebookProfiles[0].email`.

### Le champ `enrichissement`

Valeurs possibles par réseau, concaténées : `fb:<etat> ig:<etat>`.

| État | Signification |
|---|---|
| `domaine` | profil retenu par la preuve de domaine |
| `nom` | profil retenu par la preuve de nom |
| `rejete[<comptes>]` | des profils ont été trouvés **et écartés** — les noms sont consignés |
| `non_verifie` | une URL existe, mais aucun profil détaillé pour la vérifier |
| `absent` | rien trouvé |

⚠️ **`rejete[...]` nomme ce qui a été écarté.** Sans cela, un faux négatif
serait invisible : un `0` d'abonnés ne dit pas s'il n'y a pas de compte ou
si le compte a été refusé.

### Contrat d'appariement

Si le nombre de réponses Apify diffère du nombre de prospects nettoyés, le
nœud **lève une erreur**. Attribuer l'email d'une entreprise à une autre
serait bien pire qu'un champ vide.

## CT-08 — Prospect brut base de données **[révisé 04/09]**

**Source :** SQL_Get_Prospects (Postgres executeQuery)
**Cible :** Set_AI_Input

### Requête — révisée le 04/09/2026

```sql
SELECT p.*
FROM prospects p
JOIN collectes c ON p.place_id = c.place_id
WHERE c.id_campagne::text = $1;
```

Avec l'option `queryReplacement` valant `{{ $json.id_campagne }}`.

signalée par n8n lui-même. Le passage en **requête paramétrée** supprime
les deux.

## CT-09 — Contexte IA **[révisé 04/09]**

**Source :** Set_AI_Input (Set)
**Cible :** AI_Claude_Prospect_Analysis

| Champ | Type | Origine / Construction |
|---|---|---|
| `nom` | string | `nom` |
| `categorie` | string | `categorie` |
| `site_web` | string | `site_web` |
| `reseaux_sociaux` | string | template FB / LI / IG avec repli `"Non renseigné"` |
| `avis` | string | template `Note X/5 sur Y avis` |
| `metier` | string | `recherche` |
| **`audience`** | string | **[nouveau]** état réseau par réseau |
| **`fiche_google`** | string | **[nouveau]** revendiquée ou non |

### Le champ `audience` et ses trois états

Pour **chaque réseau séparément**, l'un de ces trois textes :

1. les chiffres mesurés — `« 1588 abonnés et 209 publications »`
2. `« compte existant mais statistiques NON MESURÉES »`
3. `« aucun compte trouvé, mais la détection peut avoir échoué »`

⚠️ **Pourquoi trois états et non un nombre.** Un `0` ne distingue pas
« aucun abonné » de « non mesuré ». Le 04/09, l'accroche produite pour la
« Boulangerie Les Frères Barioz » affirmait *« votre compte Instagram est
encore vide »* — alors que le compte existait, seules ses statistiques
manquaient. Dit à un prospect, c'est disqualifiant.

⚠️ **La fiabilité doit être évaluée réseau par réseau.** Une première
version la calculait globalement : Facebook mesuré rendait Instagram
« confirmé », et l'erreur ci-dessus se produisait quand même.

## CT-10 — Réponse Claude (JSON en texte) **[révisé 04/09]**

**Source :** AI_Claude_Prospect_Analysis (Anthropic Claude Sonnet)
**Cible :** Parse_AI_And_Merge

### Structure attendue — contrat imposé par le prompt

| Champ | Type | Contrainte |
|---|---|---|
| `angle` | string | 10 mots maximum, angle de prospection |
| `accroche` | string | phrase d'approche courte |
| `priorite` | string | **exactement** `1 - Haute`, `2 - Moyenne` ou `3 - Basse` |

⚠️ **Ce qui a changé.** Le contrat d'origine demandait
`"priorite": "Un chiffre entre 1 et 5"` — **sans aucun critère**. Le modèle
inventait, et un chiffre nu de 1 à 5 est illisible pour la cliente sans
légende. Les trois paliers préfixés par leur rang se trient correctement
**et** se lisent directement.

### Règle de priorisation imposée au modèle

- **RÉPUTATION ÉTABLIE** : note ≥ 4,0 sur ≥ 50 avis Google.
- **AUDIENCE SOUS-EXPLOITÉE** : le nombre d'abonnés **mesuré** le plus élevé
  (Instagram ou Facebook) est **inférieur** au nombre d'avis Google.

| Priorité | Condition |
|---|---|
| `1 - Haute` | les deux |
| `2 - Moyenne` | un seul |
| `3 - Basse` | plus d'abonnés que d'avis |

### Règle de prudence imposée au modèle

Le modèle n'a **pas le droit** d'affirmer une absence de compte, ni
d'écrire « 0 abonné », lorsque `audience` signale un réseau non mesuré. Il
ne cite un nombre d'abonnés que pour un réseau explicitement chiffré.

### Format réel retourné

La réponse est encapsulée dans `content[].text`, avec potentiellement des
balises Markdown ```` ```json ```` autour, voire une phrase avant ou après.
Le nettoyage est géré côté Parse_AI_And_Merge.

## CT-11 — Prospect enrichi fusionné **[révisé 04/09]**

**Source :** Parse_AI_And_Merge (Code JS)
**Cible :** Append row in sheet (Google Sheets)

**Fusion de :** toutes les données du prospect (depuis CT-08) + les trois
champs produits par l'IA.

### Trois garde-fous dans le code

**Contrat d'appariement.** L'analyse est recollée au prospect par son
**index**. Si le nœud IA produit un nombre d'items différent du SQL, le
code **lève une erreur** au lieu de décaler silencieusement toutes les
analyses — ce qui livrerait à la cliente des accroches attribuées au
mauvais prospect.

**Parsing tolérant.** Le premier objet `{...}` du texte est extrait, au
lieu d'exiger que toute la réponse soit du JSON. Mesure du 04/09 : **un
prospect sur cinq échouait au parsing**, et une ligne vide partait dans le
Sheet de la cliente.

**Normalisation.** Toute `priorite` hors des trois valeurs attendues
retombe sur `2 - Moyenne` avec le champ `anomalie` renseigné. Une analyse
vide écrit `A REPRENDRE - analyse IA indisponible` dans la colonne Angle :
un échec doit se voir.

**Notes de format :**

- Le téléphone est préfixé par une apostrophe pour forcer le format texte
  et éviter la perte du zéro initial.
- ⚠️ **Les colonnes d'abonnés restent vides quand le réseau n'a pas été
  mesuré**, au lieu d'afficher `0`. Une case vide se lit « on ne sait
  pas » ; un zéro se lit « aucun », et c'est faux.
- ⚠️ Le nœud fait `append`, jamais `upsert` : deux campagnes qui se
  recoupent produisent des **doublons** dans le fichier de la cliente. La
  base, elle, déduplique sur `place_id`.
