11. Plan d'Implémentation
Périmètre de ce fichier
Ce fichier décrit l'ordre dans lequel le système a été implémenté, les jalons franchis, et l'état actuel de déploiement. Il documente aussi la stratégie d'assemblage retenue (bottom-up vs top-down) et les décisions d'ordonnancement.

Ce fichier ne détaille pas les tests (voir 12.Strategie_Tests.md) ni la documentation utilisateur (voir 13.Documentation.md).

1. Stratégie d'implémentation
Approche retenue : bottom-up par service externe.

Chaque service externe (source de collecte, base de données, moteur IA, canal de restitution) a été validé isolément avant d'être intégré dans un workflow complet.

Raison de ce choix :

Chaque service a ses propres contraintes d'authentification, de format, et de limites
Valider chaque brique seule évite de chercher un bug transverse dans un workflow complexe
Permet de sécuriser les credentials un par un
2. Ordre d'assemblage
Phase 1 — Préparation de l'infrastructure
Objectif : avoir tous les accès externes fonctionnels avant d'écrire le premier workflow.

Étapes :

Instance du moteur d'orchestration déployée
Base de données créée et credentials configurés dans le moteur
Accès au service de collecte configuré
Accès au moteur IA configuré
Canal de restitution (tableur) créé et accès configuré
Jalon 1 : tous les services externes sont accessibles depuis le moteur d'orchestration.

Phase 2 — Modélisation base de données
Objectif : créer les 3 tables métier avant d'écrire les workflows qui les utilisent.

Étapes :

Création table campagnes (id_campagne PK, date_lancement, requete, zone, source, statut)
Création table prospects (place_id UNIQUE, colonnes métier complètes)
Création table collectes (id_collecte PK, id_campagne FK, place_id FK, données de collecte)
Test manuel : insertion d'une ligne dans chaque table via l'interface d'administration de la base
Jalon 2 : les 3 tables existent et acceptent des écritures.

Phase 3 — Workflow 1 (Collecte + Stockage)
Objectif : construire le workflow de collecte de bout en bout.

Étapes :

Créer le Form Trigger (C01-N01) et valider la saisie utilisateur
Ajouter le nœud Set de construction Recherche (C01-N02)
Ajouter le nœud If de validation (C02-N01) et tester les 4 conditions
Ajouter le nœud Set de préparation de la requête de collecte (C03-N01)
Ajouter le nœud d'enregistrement Campagne (INSERT en base)
Ajouter le nœud HTTP d'appel au service de collecte (C03-N02) et valider le retour brut
Ajouter le nœud de normalisation (C04-N01) et valider le mapping
Ajouter les 2 branches d'écriture (C05-N01 INSERT collectes / C05-N02 UPSERT prospects)
Ajouter les nœuds Merge + Limit
Ajouter le nœud de clôture Campagne (C06-N01)
Ajouter le nœud Execute Workflow vers WF2 (C06-N02) — désactivé temporairement
Jalon 3 : WF1 exécute une collecte complète et écrit correctement en base.

Phase 4 — Workflow 2 (Enrichissement IA + Restitution)
Objectif : construire le workflow d'enrichissement et de restitution.

Étapes :

Créer le trigger When Executed by Another Workflow
Ajouter le nœud SQL_Get_Prospects (SELECT JOIN)
Tester la récupération avec un id_campagne connu (issu de la Phase 3)
Ajouter le nœud Set_AI_Input (préparation contexte)
Ajouter le nœud AI_Claude_Prospect_Analysis (appel au moteur IA)
Valider la réponse JSON du moteur IA sur plusieurs prospects
Ajouter le nœud Parse_AI_And_Merge (Code JS) + fallback parsing
Ajouter le nœud Append row in sheet (écriture dans le canal de restitution)
Vérifier que les lignes apparaissent dans l'onglet "À trier"
Jalon 4 : WF2 exécute une analyse complète et écrit dans le canal de restitution.

Phase 5 — Intégration WF1 → WF2
Objectif : relier les 2 workflows.

Étapes :

Activer le nœud Execute Workflow (C06-N02) dans WF1
Lancer une collecte complète depuis le formulaire
Vérifier que WF2 se déclenche automatiquement
Vérifier que les prospects apparaissent enrichis dans le canal de restitution
Jalon 5 : le système fonctionne de bout en bout.

Phase 6 — Ajustements et robustesse
Objectif : corriger les cas limites découverts en test.

Étapes réalisées :

Ajout du fallback parsing dans Parse_AI_And_Merge (gestion des balises Markdown en sortie du moteur IA)
Ajout du préfixage apostrophe pour le téléphone (préservation du 0 initial dans le tableur)
Ajustement du prompt IA pour stabiliser le format JSON de sortie
Ajout du nœud Merge + Limit pour synchroniser les 2 branches d'écriture avant clôture
Jalon 6 : le système traite correctement les cas limites (parsing IA, formats données).

Phase 7 — Mise à disposition
Étapes :

Partage du canal de restitution à l'utilisatrice (accès édition)
Démonstration du formulaire de déclenchement
Explication de l'onglet "À trier" et de la colonne "Statut de qualification"
Explication de la frontière système / suivi personnel
Jalon 7 : l'utilisatrice a les accès et connaît l'utilisation du système.

4. Séquence des exécutions type
Cas nominal (lancement d'une prospection)
L'utilisatrice ouvre le formulaire de déclenchement
Elle saisit : requête, zone, limite
Elle valide → WF1 démarre
WF1 collecte via le service externe (10-30 secondes selon volume)
WF1 écrit en base et clôture la campagne
WF1 déclenche WF2
WF2 récupère les prospects et boucle sur le moteur IA (quelques secondes par prospect)
WF2 écrit chaque prospect enrichi dans le canal de restitution
L'utilisatrice consulte l'onglet "À trier" et qualifie manuellement
Durée totale estimée : 1 à 5 minutes pour 10-30 prospects.

5. Décisions d'ordonnancement notables
Pourquoi la base avant les workflows
Créer les tables avant les workflows garantit que le schéma est stable. Modifier une table après avoir écrit un workflow oblige à retoucher tous les mappings.

Pourquoi WF1 avant WF2
WF2 dépend de données existantes en base (produites par WF1). Impossible de tester WF2 sans WF1 fonctionnel — sauf à injecter manuellement des données de test.

Pourquoi Execute Workflow désactivé temporairement
Pendant le développement, activer le trigger inter-workflow trop tôt aurait déclenché WF2 à chaque test de WF1, polluant le canal de restitution avec des données de test. Désactiver ce nœud pendant Phase 3 puis l'activer en Phase 5 isole les phases de validation.
