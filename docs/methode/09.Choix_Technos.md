09. Choix Technologiques
Périmètre de ce fichier
Ce fichier nomme et décrit chaque technologie utilisée dans le système. Pour chaque technologie : son rôle, pourquoi elle a été choisie, et ce qu'elle remplace ou évite.

Les justifications approfondies et les alternatives envisagées sont dans 10.Justifications.md.

1. Vue d'ensemble de la stack
Rôle dans le système	Technologie choisie
Moteur d'orchestration	n8n (self-hosted)
Base de données relationnelle	Supabase (Postgres managé)

Moteur IA génératif	Anthropic Claude Sonnet

Hébergement n8n	VPS via automation.sterveshop.cloud
2. Détail par technologie
2.1 n8n — Moteur d'orchestration
Rôle : orchestre les 2 workflows du système. Gère le formulaire d'entrée, les appels API, les transformations de données, les écritures en base, et le déclenchement inter-workflow.

Mode : self-hosted sur VPS personnel.

Pourquoi n8n :

Interface visuelle : chaque workflow est lisible sous forme de blocs connectés
Self-hosted : les données ne passent pas par un tiers SaaS (maîtrise complète)
Gratuit en self-hosted (pas de limite de workflows ni d'exécutions)
Supporte nativement les nœuds Postgres, HTTP, Code JS, Form Trigger, Execute Workflow
Permet de prototyper et itérer rapidement sans coder un backend complet
Ce que n8n remplace :
Un développement backend custom (serveur Node.js / Python + cron + routage API) qui aurait coûté des semaines au lieu de quelques jours.

2.2 Supabase (Postgres) — Base de données
Rôle : persiste les 3 tables métier du système (campagnes, collectes, prospects). Reçoit les écritures du Workflow 1 et les lectures du Workflow 2.

Mode : instance managée Supabase (Postgres hébergé).

Pourquoi Supabase :

Postgres complet : requêtes SQL standard, jointures, upsert natif
Hébergement managé : pas de maintenance serveur BDD
Interface web pour inspecter les données manuellement
Tier gratuit suffisant pour le volume du projet (quelques centaines de prospects)
Compatible nativement avec le nœud Postgres de n8n
Ce que Supabase remplace :
Un stockage en fichiers plats ou en Google Sheets côté données (qui aurait rendu les jointures et l'upsert impossibles).

2.3 Apify — Source de collecte
Rôle : collecte les données brutes des lieux depuis Google Maps. Reçoit une requête (métier + zone) et renvoie une liste de fiches lieux avec nom, adresse, téléphone, note, avis, coordonnées.

Mode : API cloud, appel synchrone via HTTP depuis n8n.

Actor utilisé : Google Maps Scraper (nwua9Gu5YrADL7ZDj).

Pourquoi Apify :

API clé en main pour le scraping Google Maps (pas de développement crawler)
Données structurées et stables en sortie
Mode synchrone (run-sync-get-dataset-items) : un seul appel HTTP suffit, le résultat revient directement
Tarification à l'usage (pay per run)
Ce que Apify remplace :
Un crawler custom (Puppeteer / Playwright) à développer, maintenir, héberger, et adapter aux changements de Google Maps.

2.4 Anthropic Claude Sonnet — Moteur IA
Rôle : analyse chaque prospect individuellement et produit une recommandation structurée : angle de prospection, accroche personnalisée, score de priorité.

Mode : API cloud, un appel par prospect.

Modèle : Claude Sonnet (via le nœud Anthropic de n8n).

Pourquoi Claude Sonnet :

Capacité à produire du JSON structuré fiable en sortie
Compréhension fine du contexte métier francophone
Bon ratio qualité / coût pour de l'analyse unitaire de prospects
Prompt engineering simple : un seul prompt suffit pour obtenir le format voulu
Ce que Claude remplace :
Une qualification manuelle par la SMM (lire chaque fiche, imaginer un angle, rédiger une accroche) qui prendrait plusieurs minutes par prospect.

2.5 Google Sheets — Canal de restitution
Rôle : livrer les prospects enrichis à la SMM dans un format qu'elle connaît et utilise déjà. Le système écrit dans l'onglet "À trier". la SMM lit, trie, et décide.

Mode : écriture via API Google Sheets (Service Account), ligne par ligne.

Pourquoi Google Sheets :

la SMM utilisait déjà un Google Sheet pour son suivi (adoption immédiate)
Pas d'application web à construire ni à maintenir
Filtres, tris, dropdowns natifs (la SMM peut qualifier sans formation)
Partageable et accessible depuis n'importe quel appareil
Ce que Google Sheets remplace :
Un front-end CRM custom (interface web, authentification, hébergement) disproportionné pour une utilisatrice unique.

4. Credentials et accès
Tous les accès aux services externes sont gérés via le système de credentials de n8n. Les identifiants ne sont pas stockés dans le code ni dans les fichiers de configuration du repo.

Liste des credentials configurés :

Apify : authentification par header HTTP
Supabase : connexion Postgres (host, port, user, password, database)
Anthropic : clé API
Google Sheets : Service Account (clé JSON)
Aucun de ces credentials ne doit apparaître dans le repo public.
