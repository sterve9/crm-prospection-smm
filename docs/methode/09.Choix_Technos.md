## 2. Détail par technologie

### 2.1 n8n — Moteur d'orchestration

**Rôle :** orchestre les 2 workflows. Gère le formulaire d'entrée, les
appels API, les transformations, les écritures en base et le déclenchement
inter-workflow.

**Mode :** self-hosted sur VPS personnel.

**Pourquoi n8n :**

- Interface visuelle : chaque workflow est lisible sous forme de blocs
- Self-hosted : les données ne transitent pas par un tiers SaaS
- Gratuit en self-hosted, sans limite de workflows ni d'exécutions
- Nœuds natifs Postgres, HTTP, Code JS, Form Trigger, Execute Workflow
- Permet de prototyper sans coder un backend complet

**Ce que n8n remplace :** un développement backend custom — serveur
Node.js/Python + cron + routage API — qui aurait coûté des semaines.

**[relevé 04/09] Deux comportements à connaître :**

- **L'historique d'exécution est purgé** au-delà d'une quinzaine de jours.
  Quand une campagne échoue chez l'utilisatrice, il ne reste aucune trace
  exploitable pour diagnostiquer.
- **Les données épinglées ne s'appliquent qu'aux exécutions manuelles**
  lancées depuis l'éditeur. C'est ce qui permet de rejouer un workflow aval
  sans repayer l'amont. Voir `10.Justifications.md` (**D-23**).

### 2.2 Supabase (Postgres) — Base de données

**Rôle :** persiste les 3 tables métier — `campagnes`, `collectes`,
`prospects`. Reçoit les écritures de WF1 et les lectures de WF2.

**Mode :** instance managée Supabase.

**Pourquoi Supabase :**

- Postgres complet : SQL standard, jointures, upsert natif
- Hébergement managé, aucune maintenance serveur
- Interface web pour inspecter les données manuellement
- Tier gratuit suffisant pour le volume du projet
- Compatible nativement avec le nœud Postgres de n8n

**Ce que Supabase remplace :** un stockage en fichiers plats ou dans un
tableur, qui aurait rendu jointures et upsert impossibles.

⚠️ **[relevé 04/09]** Le tier gratuit **ne conserve pas de sauvegarde
ponctuelle restaurable en un clic**. Une suppression de données est
irréversible : compter avant de supprimer.

### 2.3 Apify — Source de collecte

**Rôle :** collecte les données brutes des lieux depuis Google Maps.
Reçoit une requête et renvoie une liste de fiches.

**Mode :** API cloud, appel synchrone via HTTP depuis n8n.

**Acteur utilisé :** Google Maps Scraper (`nwua9Gu5YrADL7ZDj`).

**Pourquoi Apify :**

- API clé en main, pas de crawler à développer
- Données structurées et stables en sortie
- Mode synchrone (`run-sync-get-dataset-items`) : un seul appel HTTP
- Tarification à l'usage

**Ce que Apify remplace :** un crawler custom — Puppeteer, Playwright — à
développer, maintenir, héberger et adapter aux changements de Google Maps.

#### **[révisé 04/09]** Options activées, et ce qu'elles coûtent

| Option | Valeur | Effet |
|---|---|---|
| `locationQuery` | la zone demandée | **contrainte géographique réelle** |
| `scrapeContacts` | `true` | extraction des emails et téléphones |
| `scrapeSocialMediaProfiles` | Facebook, Instagram, TikTok | profils avec abonnés et publications |
| `skipClosedPlaces` | `true` | écarte les établissements fermés |

⚠️ **`locationQuery` n'est pas une option de confort, c'est une
correction.** Avant le 04/09, la zone était concaténée à la recherche : le
service traitait « boulangerie lyon » en texte libre et renvoyait des
commerces situés sur des rues nommées « Lyon », jusqu'en Dordogne. Voir
**D-16**.

⚠️ **`scrapeContacts` fait visiter chaque site web par Apify.** Le coût par
résultat **et** la durée du run augmentent. Mesure du 04/09 : **34 secondes
pour 5 prospects**. L'appel étant synchrone et borné dans le temps, le
comportement au-delà de quelques dizaines de prospects **n'est pas
éprouvé**. Voir **D-17**.

⚠️ **Ne jamais activer de reprise automatique sur cet appel.** `run-sync`
lance une exécution facturée puis attend : une reprise lance une **seconde
collecte payante**. Voir **D-23**.

#### **[relevé 04/09]** Deux champs de sortie à traiter avec précaution

- **`phonesUncertain`** est inexploitable : horodatages, suites de chiffres
  absurdes. À ignorer entièrement.
- **Les tableaux `facebooks`, `instagrams`, `linkedIns`** contiennent tous
  les réseaux trouvés dans la page, **hébergeur compris**. Ils ne peuvent
  pas être utilisés sans vérification d'appartenance. Voir **D-18**.

En revanche, le champ **`domain`** et les objets `facebookProfiles` /
`instagramProfiles` — avec `externalProfileURL`, `followersCount`,
`postsCount` — sont ce qui rend cette vérification possible. Sans eux,
aucun tri fiable ne serait faisable.

### 2.4 Anthropic Claude Sonnet — Moteur IA

**Rôle :** analyse chaque prospect et produit une recommandation
structurée : angle de prospection, accroche personnalisée, priorité.

**Mode :** API cloud, un appel par prospect.

**Pourquoi Claude Sonnet :**

- Capacité à produire du JSON structuré fiable
- Compréhension fine du contexte métier francophone
- Bon ratio qualité / coût pour de l'analyse unitaire
- Prompt engineering simple

**Ce que Claude remplace :** une qualification manuelle par la SMM — lire
chaque fiche, imaginer un angle, rédiger une accroche — qui prendrait
plusieurs minutes par prospect.

⚠️ **[mesuré 04/09] « Fiable » n'est pas « garanti ».** Sur une campagne de
cinq prospects, **une réponse sur cinq** n'était pas parsable en l'état.
Le système ne suppose donc plus la conformité : il extrait le premier objet
JSON du texte, et signale l'échec quand il survient. Voir **D-11** et
**D-20**.

⚠️ **[relevé 04/09]** Aucun `max_tokens` n'est défini sur le nœud. Une
réponse tronquée reste une cause possible d'échec de parsing, non écartée.

### 2.5 Google Sheets — Canal de restitution

**Rôle :** livrer les prospects enrichis dans un format que la SMM connaît
et utilise déjà. Le système écrit dans l'onglet « À trier » ; elle lit,
trie et décide.

**Mode :** écriture via API Google Sheets (Service Account), ligne par ligne.

**Pourquoi Google Sheets :**

- La SMM utilisait déjà un Google Sheet — adoption immédiate
- Aucune application web à construire ni maintenir
- Filtres, tris et listes déroulantes natifs, sans formation
- Partageable et accessible depuis n'importe quel appareil

**Ce que Google Sheets remplace :** un front-end CRM custom — interface,
authentification, hébergement — disproportionné pour une utilisatrice unique.

⚠️ **[relevé 04/09] L'écriture se fait par ajout, sans déduplication.** La
base déduplique sur `place_id`, le tableur non. Deux campagnes qui se
recoupent produisent des doublons visibles. Voir **D-12**.

⚠️ **Le nœud écrit par nom de colonne.** Renommer un en-tête dans le
tableur casse l'écriture silencieusement tant que le mapping n'est pas mis
à jour du même geste.

## 3. Résumé du flux technologique

```
la SMM (navigateur)
    |
    v
n8n Form Trigger
    |
    v
n8n Workflow 1
    |
    +---> Apify API           collecte Google Maps + contacts + réseaux
    |
    +---> Supabase Postgres   écriture campagnes, collectes, prospects
    |
    v
n8n Workflow 2
    |
    +---> Supabase Postgres   lecture des prospects de la campagne
    |
    +---> Anthropic Claude    analyse et priorisation
    |
    +---> Google Sheets API   écriture onglet « À trier »
    |
    v
la SMM (Google Sheet)
```

## 4. Credentials et accès

Tous les accès aux services externes sont gérés via le système de
credentials de n8n. Les identifiants ne sont stockés ni dans le code ni
dans les fichiers de configuration du dépôt.

**Credentials configurés :**

| Service | Type d'authentification |
|---|---|
| Apify | header HTTP |
| Supabase | connexion Postgres (host, port, user, password, database) |
| Anthropic | clé API |
| Google Sheets | Service Account (clé JSON) |

**Aucun de ces credentials ne doit apparaître dans le dépôt public.**
