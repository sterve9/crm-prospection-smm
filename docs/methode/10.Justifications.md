10. Justifications des Choix
Périmètre de ce fichier
Ce fichier documente les décisions structurantes prises pendant la conception et l'implémentation du système. Pour chaque décision : le contexte, les alternatives envisagées, le choix retenu, et les conséquences (positives et négatives).

Ce fichier assume aussi les fragilités connues et documentées, plutôt que de les cacher.

1. Décisions métier structurantes
D-01 — Utilisatrice unique : la SMM
Contexte : Le système est développé pour la SMM uniquement, dans le cadre d'un contrat gratuit contre témoignage.

Alternatives envisagées :

Système multi-utilisateurs dès le départ (authentification, isolation des données)
Système générique adaptable à d'autres Social Media Managers
Choix retenu : utilisatrice unique, pas d'authentification, pas d'isolation multi-tenant.

Conséquences :

(+) Simplicité maximale, temps de développement réduit
(+) Pas de couche d'authentification à maintenir
(-) Si le système doit être étendu à d'autres utilisatrices, une refonte partielle sera nécessaire
D-02 — Aucune décision commerciale automatisée
Contexte : Le besoin de la SMM est d'être aidée dans le tri et l'analyse, pas d'être remplacée dans la décision commerciale.

Alternatives envisagées :

Envoi automatique d'emails aux prospects qualifiés
Auto-validation des prospects avec score de priorité élevé
Choix retenu : l'IA propose (angle, accroche, priorité), la SMM décide seule qui contacter.

Conséquences :

(+) Respect strict du besoin exprimé
(+) Aucun risque de dérive commerciale automatisée
(+) la SMM reste maîtresse de sa relation client
(-) Le système ne peut pas mesurer son propre impact commercial (métriques hors périmètre)
D-03 — Objet central = Prospect
Contexte : Choix de l'objet racine du domaine métier. Test d'écroulement appliqué aux 4 objets candidats (Prospect, Campagne, Collecte, Qualification).

Alternatives envisagées :

Campagne comme objet central (approche "processus")
Qualification comme objet central (approche "état")
Choix retenu : Prospect. Sans prospect, aucun autre objet n'a de sens.

Conséquences :

(+) Modèle de données stable et intuitif
(+) Cycle de vie clair (3 états)
(+) Le système reste pertinent même si la notion de campagne évolue
D-04 — Qualification = objet séparé (préservation d'historique)
Contexte : La qualification IA (angle, accroche, priorité) pourrait être fusionnée dans l'objet Prospect. Mais un prospect peut être re-qualifié plusieurs fois si les données évoluent.

Alternatives envisagées :

Fusionner angle/accroche/priorité directement dans la table prospects
Écraser à chaque nouvelle analyse
Choix retenu : documenter la qualification comme objet métier séparé, même si dans l'implémentation actuelle elle est injectée directement dans le Google Sheet sans table dédiée en base.

Conséquences :

(+) Le modèle métier reste extensible (une table qualifications pourra être ajoutée si besoin)
(-) Pour l'instant, l'historique des qualifications n'est pas conservé côté base (seule la dernière analyse existe, dans le Sheet)
Note d'évolution : si la SMM demande à re-lancer des analyses IA sur d'anciens prospects, il faudra créer la table qualifications.
D-05 — Feuille de suivi n'est pas un objet métier
Contexte : Le Google Sheet contient plusieurs onglets, dont "CRM SMM" (suivi personnel de la SMM). Question : cet onglet fait-il partie du modèle métier du système ?

Choix retenu : non. Le Google Sheet est un canal de sortie, pas un objet métier. Ce qui se passe dans l'onglet "CRM SMM" est hors périmètre système.

Conséquences :

(+) Frontière système / humain clairement posée
(+) Le système n'a pas à connaître ni gérer le workflow commercial personnel de la SMM
2. Décisions techniques structurantes
D-06 — id_campagne = ID d'exécution n8n
Contexte : Chaque campagne doit avoir un identifiant unique. Plusieurs options possibles pour générer cet ID.

Alternatives envisagées :

UUID généré par n8n (nœud Code JS)
Séquence auto-incrémentée par Postgres
Utiliser l'ID d'exécution n8n natif ($execution.id)
Choix retenu : $execution.id — l'ID d'exécution n8n est utilisé directement comme id_campagne.

Conséquences :

(+) Unicité garantie par nature (n8n génère un ID unique par exécution)
(+) Traçabilité : on peut retrouver l'exécution n8n correspondant à une campagne
(+) Zéro logique de génération à coder
(-) La campagne est liée conceptuellement au moteur d'orchestration : si on change de moteur, il faudra migrer cette logique
(-) Un ID n8n n'a pas de sémantique métier (ce n'est pas un numéro séquentiel humainement lisible)
Décision assumée : la dépendance à n8n est acceptée car changer de moteur d'orchestration impliquerait de toute façon une refonte majeure.

D-07 — Trigger inter-workflow sans mapping explicite (fragilité assumée)
Contexte : Le Workflow 1 déclenche le Workflow 2 via le nœud Execute Workflow. Ce nœud permet de mapper explicitement les données transmises au workflow appelé.

Configuration observée :

workflowInputs.value : {} (vide)
inputSource côté WF2 : passthrough
Alternatives envisagées :

Mapper explicitement id_campagne dans workflowInputs (comportement recommandé)
Passer par un webhook intermédiaire
Choix retenu (par défaut historique) : aucun mapping explicite. WF2 accède à id_campagne via le passthrough des données en amont.

Conséquences :

(+) Fonctionne dans le contexte actuel (WF2 est toujours appelé par WF1 juste après la clôture campagne)
(-) Fragilité identifiée : si un jour WF2 est appelé depuis un autre contexte, id_campagne pourrait ne pas être présent
(-) Le contrat inter-workflow n'est pas explicite dans la configuration n8n (il faut lire le code JS pour le comprendre)
Décision à revoir : cette configuration devrait être corrigée en ajoutant un mapping explicite id_campagne dans le nœud Execute Workflow de C06-N02. Marqué comme dette technique.

D-08 — 2 workflows séparés plutôt qu'un seul workflow long
Contexte : Toute la logique (collecte + IA + restitution) aurait pu tenir dans un seul workflow n8n.

Alternatives envisagées :

Un seul workflow monolithique de 15+ nœuds
Deux workflows séparés reliés par Execute Workflow
Choix retenu : deux workflows séparés.

Conséquences :

(+) Séparation claire des responsabilités : collecte / enrichissement
(+) Possibilité de relancer WF2 seul si besoin (ré-analyse IA sans re-scraping)
(+) Lisibilité visuelle : chaque workflow tient sur un écran
(+) Debugging plus simple (isoler un problème à un workflow)
(-) Un contrat inter-workflow à maintenir (voir D-07)
D-09 — Upsert sur place_id plutôt qu'INSERT ignoré
Contexte : Un prospect peut être collecté plusieurs fois si la SMM relance une prospection sur la même zone / métier.

Alternatives envisagées :

INSERT strict avec gestion d'erreur "duplicate key"
INSERT ignoré (ON CONFLICT DO NOTHING)
UPSERT (INSERT ou UPDATE si existant)
Choix retenu : UPSERT sur place_id.

Conséquences :

(+) La fiche prospect est toujours à jour (dernière note Google, dernier nombre d'avis)
(+) Pas de doublon en base
(-) L'historique des changements n'est pas conservé sur la table prospects (mais il l'est indirectement via la table collectes, qui garde une trace par passage)
D-10 — Double branche INSERT collectes / UPSERT prospects
Contexte : À chaque collecte, il faut à la fois tracer le passage (table collectes) et mettre à jour la fiche consolidée (table prospects).

Choix retenu : 2 branches parallèles depuis C04-N01, synchronisées par Merge + Limit avant la clôture de campagne.

Conséquences :

(+) Séparation nette : collectes = historique, prospects = état courant
(+) On peut compter les passages par prospect via la table collectes
(-) Complexité visuelle légèrement supérieure (2 branches à suivre dans n8n)
D-11 — Prompt Claude → JSON structuré
Contexte : L'IA doit produire une réponse exploitable par le workflow. Options : texte libre, JSON, YAML.

Alternatives envisagées :

Texte libre (à parser manuellement)
Function calling / structured output (feature Anthropic récente)
JSON dans un prompt structuré
Choix retenu : JSON dans un prompt structuré, avec parsing JS côté n8n (Parse_AI_And_Merge).

Conséquences :

(+) Simplicité : un seul prompt, un seul parse
(+) Fallback géré (angle "Erreur de parsing" si le JSON est invalide)
(-) Dépendance à la capacité du modèle à respecter le format (Claude Sonnet est fiable, mais pas 100%)
Évolution possible : passer au Function Calling / Structured Output natif d'Anthropic pour éliminer le risque de parsing.
D-12 — Google Sheets écriture ligne par ligne (append)
Contexte : Chaque prospect enrichi doit apparaître dans le Sheet. Options : batch, append unitaire.

Choix retenu : append ligne par ligne (une exécution du nœud Google Sheets par prospect).

Conséquences :

(+) Simplicité de configuration
(+) Si un prospect échoue à l'IA, les autres passent quand même
(-) Un appel API Google Sheets par prospect (potentiellement lent sur grosses campagnes)
Point de vigilance : au-delà de 100+ prospects par campagne, envisager un batch write.
D-13 — Téléphone stocké en texte forcé dans Google Sheets
Contexte : Les numéros de téléphone français commencent par 0. Google Sheets convertit automatiquement les chaînes numériques en nombres, ce qui supprime le 0 initial.

Alternatives envisagées :

Formater la colonne en texte manuellement dans Sheets
Préfixer chaque téléphone d'une apostrophe (forçage texte natif Sheets)
Choix retenu : préfixage par apostrophe dans le nœud Google Sheets ("='{{ $json.telephone }}").

Conséquences :

(+) Le format téléphone est préservé
(-) L'apostrophe est visible si on inspecte la cellule (mais pas dans l'affichage)
3. Décisions de méthode / documentation
D-14 — Application de la méthode standard 13 étapes
Contexte : Ce projet est le premier projet réel construit par l'architecte. Il sert de base à la standardisation de la méthode.

Choix retenu : appliquer rétroactivement la méthode 13 étapes au projet, même si les fichiers ont été écrits dans un ordre différent pendant le développement.

Conséquences :

(+) Ce projet devient un exemple concret réutilisable
(+) La méthode est éprouvée sur un cas réel avant d'être théorisée
(-) Certains fichiers ont dû être réécrits (ex : 06.Composants.md, corrigé en reprise)
D-15 — Documentation publique (repo GitHub) sans secrets
Contexte : Le repo GitHub doit être public pour servir d'exemple (vidéo TikTok, portfolio).

Choix retenu : aucun credential, ID de credential n8n, URL d'instance privée, ou clé API n'apparaît dans le repo. Les workflows JSON exportés sont nettoyés avant commit.

Conséquences :

(+) Le repo peut être partagé sans risque de fuite
(+) Les workflows JSON restent lisibles et réutilisables (structure visible, credentials à re-configurer par le lecteur)
