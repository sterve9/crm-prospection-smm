13. Documentation
Périmètre de ce fichier
Ce fichier décrit comment est organisée la documentation du projet : la structure des dossiers, l'ordre de lecture recommandé, les conventions utilisées, et les règles de mise à jour.

Il sert de point d'entrée à toute personne qui découvre le repo.

1. Structure de la documentation
La documentation du projet est organisée en 13 fichiers standard, un par étape de la méthode. Chaque fichier a un périmètre strict et ne déborde pas sur les autres.

3. Ordre de lecture recommandé
Pour comprendre le POURQUOI du système
Lire dans l'ordre : 01 → 02 → 03 → 04 → 05

Ces 5 fichiers décrivent le domaine métier sans aucune considération technique. À la fin de cette lecture, on comprend le besoin, le problème, et le modèle métier.

Pour comprendre le COMMENT du système
Lire dans l'ordre : 06 → 07 → 08

Ces 3 fichiers décrivent la structure fonctionnelle : les blocs, les contrats de données entre eux, et l'architecture d'ensemble. Toujours sans nommer les technologies.

Pour comprendre les CHOIX techniques
Lire dans l'ordre : 09 → 10

Ces 2 fichiers nomment les technologies et justifient chaque choix, y compris les fragilités assumées.

Pour reproduire ou étendre le système
Lire dans l'ordre : 11 → 12

Ces 2 fichiers décrivent l'ordre d'implémentation et la stratégie de validation.

4. Principes de rédaction
4.1 Un fichier = un périmètre strict
Chaque fichier ne contient QUE ce que son titre annonce. Un lecteur qui ouvre 03.Objets_Metier ne doit pas y trouver de considérations sur les contrats de données, la stack technique, ou les décisions d'implémentation.

Chaque fichier se termine par une section "Ce que ce fichier ne contient PAS" avec des renvois explicites vers les fichiers concernés.

4.2 Pas de technologie avant l'étape 09
Les fichiers 01 à 08 ne nomment aucune technologie propriétaire. Ils parlent en termes de rôles fonctionnels (moteur d'orchestration, base de données relationnelle, service de collecte, moteur IA, canal de restitution).

Cette règle garantit que le modèle métier et l'architecture restent lisibles indépendamment des choix techniques, et facilite une éventuelle migration technologique future.

4.3 Documenter les fragilités assumées
Les points de fragilité connus ne sont pas cachés : ils sont documentés dans 10.Justifications.md avec leur contexte, leur impact, et le raisonnement qui les a fait accepter.

4.4 Références croisées explicites
Quand un fichier fait référence à une information contenue dans un autre, le renvoi est explicite : "voir 07.Contrats.md, CT-05" plutôt qu'une allusion vague.

6. Conventions
6.1 Nommage des composants
CXX-NYY : nœud technique du workflow (ex : C05-N01)
CT-XX : contrat de données (ex : CT-05)
D-XX : décision documentée (ex : D-07)
EX : état du cycle de vie (ex : E1)
TX : transition du cycle de vie (ex : T1)
6.2 Format des fichiers
Tous les fichiers sont en Markdown (.md)
Encodage UTF-8
Fins de ligne LF (Unix)
6.3 Langue
Toute la documentation est rédigée en français.

7. Règles de mise à jour
7.1 Quand mettre à jour la doc
La documentation doit être mise à jour dans les cas suivants :

Ajout ou modification d'un composant du système
Modification d'un contrat de données
Ajout d'un service externe ou changement de technologie
Décision structurante prise pendant une évolution
Correction d'une fragilité documentée
7.2 Ordre de mise à jour
Lors d'une évolution du système, mettre à jour les fichiers dans l'ordre inverse de la lecture :

Modifier d'abord 06, 07, 08 (structure) si nécessaire
Puis 09, 10 (choix et justifications)
Puis 11, 12 (implémentation et tests)
Les fichiers 01 à 05 (domaine métier) ne devraient être modifiés qu'en cas de changement fondamental du besoin.

7.3 Traçabilité
Chaque évolution majeure devrait donner lieu à :

Une mise à jour des fichiers concernés
Une nouvelle décision documentée dans 10.Justifications.md (si arbitrage)
8. Comment utiliser cette documentation
8.1 Pour un nouvel arrivant sur le projet
Ordre recommandé : lire le README puis 01 à 13 dans l'ordre. Compter environ 1h de lecture pour comprendre le système en profondeur.

8.2 Pour reproduire un système similaire
Utiliser les 13 fichiers comme un canevas. Chaque fichier a un rôle précis dans la démarche : commencer par 01 (besoin), finir par 12 (tests).

8.3 Pour auditer un point précis
Utiliser le tableau de la section 2 pour identifier le fichier concerné directement, sans lire le reste.

8.4 Pour comprendre une fragilité ou un choix contre-intuitif
Consulter directement 10.Justifications.md et chercher la décision (D-XX) correspondante.

9. Statut de la documentation
Cette documentation est complète et couvre le système tel qu'il est déployé au moment de sa rédaction.

Elle sera mise à jour à chaque évolution significative du système.
